# 渐进迁移计划

## 原则

本仓库采用独立、干净的公开历史。每批内容先完成白名单审查，再迁移和验证；不自动导入旧仓库的 Git 历史、issue、PR、日志或运维记录。

现有服务继续独立运行。公开代码迁移不代表生产切换、数据迁移或旧系统下线。

## 公开内容边界

可候选迁移：通用核心、模块契约、去实例化代码、合成示例、经过审查的测试及通用部署模板。

必须保留私有：真实凭据、实例配置、内部拓扑、生产数据、运行日志、人员目录、生产故障原料、发布和回滚履历。不得把这些内容写进公开文档、提交信息、PR 描述、CI 日志或产物。

公开示例须采用合成数据和占位参数，不能依赖实际业务环境。版权与第三方许可审查是迁移门槛的一部分。

## 阶段

1. **公开基础**：项目说明、迁移边界和贡献流程；建立允许公开的文件清单。
2. **可运行骨架**：工作台入口、模块注册与合成数据演示；明确安装和最低运行版本。
3. **协作能力**：逐项迁移只读投影、责任田候选和配置等能力，分别标明支持范围与限制。
4. **CI 与制品**：通过适配器接入；补齐受控下载、凭据作用域与任务隔离，不携带真实上游配置。
5. **工作空间**：在明确资源和授权契约后实现并验证空间自治、数据隔离和显式共享。
6. **后续研发辅助能力**：根据源码访问、工具执行和会话隔离的安全验收逐步迁移。

每个阶段单独交付和验收，不以文档或导航入口代替功能完成。

## 每批迁移的验收门槛

- 记录迁入文件清单，保留必要版权与署名；来源证据在合适的私有记录中保存，不公开私有运维信息。
- 运行内容、凭据与敏感信息检查，并人工检查示例、截图和产物。
- 不引入现有生产网络、私有凭据或持久自托管 runner。
- 面向不可信 PR 的 CI 使用无生产访问能力的一次性隔离执行环境；集成和部署流程另行设计。
- 适用测试、文档链接及许可证检查通过；未执行的检查必须明确标注。
- 说明配置/API/数据兼容性、维护主线与必要回退方案。

## 当前可运行内容与未完成边界

已提供独立的[本地合成演示](runnable-demo.md)，以及另外显式配置的
[统一服务与产品入口](unified-entry.md)。后者已有 SQLite 工作空间策略、
成员与操作员持久授权、管理员/邀请操作、Cookie/session 事务边界及分模块的
只读快照、审核和受控获取能力。不同模块的接入范围与剩余门禁以能力地图和
各包契约为准；合成演示不因此成为已认证的生产应用。

工作空间自治与隔离正按可单独验收的切片实现，不再仅停留在设计阶段，但这
不表示多租户隔离或 OBS 整体迁移已完成。新建空间的 initial-admin 选择预条件
延续既有平台治理边界，验收另见[计划](../packages/workspace_admin_api/tests/README.md#initial-admin-selection-acceptance-plan)。
真实 GitCode 登录与身份变更仍硬关闭；旧授权恢复、真实上游兼容和生产迁移
仍需独立审查。公开 CI 独立交付，本计划不宣称新增检查已通过，也不包含部署、
生产数据迁移或旧系统下线。
